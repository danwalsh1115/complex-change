## Why this talk

Organizations trying to transform usually reach for recipes and "best practices." That works when cause and effect are known in advance. Most real change, especially change in culture, behavior and ways of working, isn't like that. It is **complex**: you only understand cause and effect in hindsight, and the system changes as you act on it.

This talk uses the **Cynefin Framework** to show leaders and change agents:

- why so many change efforts fail when they're run like engineering projects
- how to tell which kind of situation you're actually in
- how to tailor methods and decisions to that situation
- practical heuristics for working with complexity instead of against it

---

## The Cynefin Framework at a glance

| Domain | What it's like | How to act | Practice that fits |
|---|---|---|---|
| **Obvious** (now called *Clear*) | Cause and effect are plain to everyone | Sense → Categorize → Respond | Best practice, checklists |
| **Complicated** | Cause and effect can be worked out by experts | Sense → Analyze → Respond | Good practice, expert analysis |
| **Complex** | Cause and effect are only clear in hindsight | Probe → Sense → Respond | Emergent practice, safe-to-fail experiments |
| **Chaotic** | No discernible cause and effect | Act → Sense → Respond | Novel practice, stabilize first |
| **Disorder** (now called *Confused*) | You don't know which domain you're in | Break the situation into parts | Assign each part to a domain |

The key move for change agents: **stop treating complex problems as complicated ones.** More analysis and a better plan won't help when the answer can only emerge from trying things.

---

## Heuristics for complex change

These are the heuristics the talk covers for working in the complex domain:

| Heuristic | In practice |
|---|---|
| **Manage in the present** | Start from where the system is today, not from an idealized future state |
| **Small bets** | Run several safe-to-fail experiments in parallel; amplify what works and dampen what doesn't |
| **Nudges** | Shift conditions and incentives slightly rather than mandating large changes |
| **Simple rules** | Give people a few clear principles that guide behavior instead of detailed procedures |
| **Disintermediation** | Shorten the distance between decision-makers and the people and data closest to the work |
| **Distributed cognition** | Use many perspectives across the organization to make sense of what's happening |

## Why this still matters for product and AI work

The same thinking shows up in how I run product today: discovery is complex-domain work, so it runs on small, safe-to-fail bets; AI and ML features need evaluation criteria defined before building, because their behavior emerges rather than being specified; and platform rollouts go better with a few simple rules than with long procedures.
